Safari Refinements · JSX W&D v4.0
Safari Fixes
Handoff

JSX W&D runs well on Chrome and Brave. Safari — particularly iOS Safari — has 15 specific issues caused by the combination of backdrop-filter, variable fonts, clip-path animations, canvas grain, WebGL, mix-blend-mode, Lenis, and position:fixed. Every issue is documented here with the exact code fix. All are copy-paste ready.

P1 — Critical · Fix first, visible immediately
P2 — High · Fix in first pass
P3 — Medium · Fix before launch

Detection
Browser Utilities

Put this block in a single shared utility file — src/lib/browser.ts — and import the constants wherever needed. Do not repeat these detections inline across multiple components.

src/lib/browser.ts — copy this entire file
// ── Browser & device detection ──────────────────────────────────────────
// Import these constants wherever you need browser-conditional behaviour.
// All are safe to call client-side only — wrap in useEffect or check window.

export const isSafari =
  typeof window !== 'undefined' &&
  /^((?!chrome|android).)*safari/i.test(navigator.userAgent)

export const isIOSSafari =
  typeof window !== 'undefined' &&
  /iP(ad|hone|od)/.test(navigator.userAgent) &&
  /WebKit/.test(navigator.userAgent) &&
  !('MSStream' in window)

export const isTouch =
  typeof window !== 'undefined' &&
  ('ontouchstart' in window || navigator.maxTouchPoints > 0)

export const isMobile =
  typeof window !== 'undefined' &&
  /iPhone|iPad|iPod|Android/i.test(navigator.userAgent)

export const prefersReducedMotion =
  typeof window !== 'undefined' &&
  window.matchMedia('(prefers-reduced-motion: reduce)').matches

// Safari version — useful for targeting specific Safari bugs
export function getSafariVersion(): number {
  if (!isSafari) return 0
  const match = navigator.userAgent.match(/Version\/(\d+)/)
  return match ? parseInt(match[1]) : 0
}

// Feature detection (better than UA sniffing where possible)
export const supportsBackdropFilter =
  typeof CSS !== 'undefined' &&
  (CSS.supports('backdrop-filter', 'blur(1px)') ||
   CSS.supports('-webkit-backdrop-filter', 'blur(1px)'))

export const supportsMixBlendMode =
  typeof CSS !== 'undefined' &&
  CSS.supports('mix-blend-mode', 'difference')

export const supportsInset =
  typeof CSS !== 'undefined' &&
  CSS.supports('inset', '0')
Testing
How to Test in Safari
Desktop Safari
Safari → Develop menu → Enable (if not visible: Safari Preferences → Advanced → Show Develop menu). Open DevTools with Cmd+Option+I. Use the Responsive Design Mode (Develop → Enter Responsive Design Mode) to test different iPhone/iPad viewport sizes without a device.
Real iOS device
Connect iPhone/iPad via USB. Safari → Develop → [Your Device Name] → [Page]. This gives you full DevTools on the device's actual Safari. Always test on a real device — the simulator doesn't reproduce all iOS Safari bugs, especially the memory crash and fixed-position jump.
BrowserStack
If no Apple device available: browserstack.com — free trial gives real device testing on iOS Safari. Use iPhone 13/14 with Safari 16+ as primary target, and iPhone 12 with Safari 15 as secondary.
Version targets
Safari 17 (current) — full support. Safari 16 — target minimum. Safari 15 — check for svh unit. Safari 14 — check inset and gap. Safari 13 — flex gap only, don't invest heavily here.
Test order

Always test the P1 fixes first with the page at rest (not scrolling). Then test scroll-driven effects. Then test hover interactions with a mouse on Safari desktop. Then test on an actual iOS device. Each layer can reveal different problems.

Fix 01
backdrop-filter P1 Critical
Priority
P1
Fix first
What breaks
The pill nav, contact modal, Lisa assistant panel, and filter bar all use backdrop-filter: blur(). In Safari without the -webkit- prefix, the blur does not render. The background becomes either fully transparent or a solid colour with no blur effect — making the pill nav look like a broken strip and the modals look like flat boxes.
Why
Safari requires -webkit-backdrop-filter alongside the unprefixed version. Without it Safari simply ignores the property entirely. This has been the case since Safari first implemented backdrop-filter in version 9.
Affected files
globals.css or component CSS — anywhere backdrop-filter appears. Search the entire codebase for the string backdrop-filter and apply the fix to every instance.
/* BEFORE — Safari ignores this */
.pill-track {
  backdrop-filter: blur(28px) saturate(180%);
}

/* AFTER — add -webkit- prefix immediately above every instance */
.pill-track {
  -webkit-backdrop-filter: blur(28px) saturate(180%); /* Safari */
          backdrop-filter: blur(28px) saturate(180%); /* All others */
}

Apply to all four affected elements:

.pill-track {
  -webkit-backdrop-filter: blur(28px) saturate(180%);
          backdrop-filter: blur(28px) saturate(180%);
}
.modal {
  -webkit-backdrop-filter: blur(32px);
          backdrop-filter: blur(32px);
}
#lisa-panel {
  -webkit-backdrop-filter: blur(24px);
          backdrop-filter: blur(24px);
}
.filter-bar {
  -webkit-backdrop-filter: blur(16px);
          backdrop-filter: blur(16px);
}
#modal-bg {
  -webkit-backdrop-filter: blur(20px);
          backdrop-filter: blur(20px);
}
Quick verification

Open the site in Safari, open DevTools, click the pill nav. If you see backdrop-filter in the Styles panel with a strikethrough, the prefix is missing. After adding the prefix, the strikethrough disappears and the blur renders correctly.

Fix 02
100vh on iOS P1 Critical
Priority
P1
Fix first
What breaks
On iOS Safari, 100vh is calculated including the browser chrome (address bar + tab bar). When the address bar is visible, the hero section is taller than the actual visible area. The bottom stats bar gets pushed below the fold and isn't visible without scrolling.
Why
Apple's intentional design decision — 100vh in iOS Safari represents the maximum possible viewport height (browser chrome hidden), not the current visible height. Chrome/Firefox match the actual visible area instead.

Modern fix — use svh (small viewport height), supported in Safari 15.4+:

#hero {
  min-height: 100svh; /* Safari 15.4+ — excludes browser chrome */
  min-height: 100vh;  /* Fallback for older Safari */
}

/* Also fix the word builder sticky container */
#word-build-sticky {
  height: 100svh;
  height: 100vh; /* fallback */
}

Older iOS fallback — if you need to support Safari 14 and below:

// In layout.tsx or a client component — run once on mount
useEffect(() => {
  function setVH() {
    const vh = window.innerHeight * 0.01
    document.documentElement.style.setProperty('--vh', `${vh}px`)
  }
  setVH()
  window.addEventListener('resize', setVH)
  return () => window.removeEventListener('resize', setVH)
}, [])

/* Then in CSS — use the variable with vh fallback */
#hero {
  min-height: calc(var(--vh, 1vh) * 100);
}
Fix 03
inset Shorthand P1 Critical
Priority
P1
Fix first
What breaks
The grain canvas, page background overlay, spotlight div, preloader, shuffle overlay, modal background, and Easter egg all use inset: 0 as shorthand for top: 0; right: 0; bottom: 0; left: 0. Safari 14 and below doesn't support this shorthand — these elements don't cover the full screen, causing layout breaks or partial overlays.
Scope
Do a global find-and-replace across all CSS and styled components. Search for inset: 0 and replace with the explicit four-property version. Safari 15+ supports inset, but replacing it costs nothing and fixes Safari 14.
/* BEFORE */
#grain, #trail-canvas, #page-bg, #spot,
#preloader, #shuffle-overlay, #modal-bg, #egg {
  inset: 0;
}

/* AFTER — explicit, works on Safari 14+ */
#grain, #trail-canvas, #page-bg, #spot,
#preloader, #shuffle-overlay, #modal-bg, #egg {
  top: 0;
  right: 0;
  bottom: 0;
  left: 0;
}
Note

inset for non-zero values (e.g. inset: 0 24px) also needs the same treatment. Check for any other inset usages beyond inset: 0.

Fix 04
Gradient Text P1 Critical
Priority
P1
Fix first
What breaks
The animated gradient on "impossible to ignore" in the hero description renders as a solid lime block in Safari instead of showing the gradient sweep. The text is visible but the gradient animation doesn't work.
Why
Two issues: (1) background-clip: text requires the -webkit-background-clip: text prefix in Safari. (2) color: transparent must be replaced with -webkit-text-fill-color: transparent — Safari handles text colour clipping differently from other browsers.
/* BEFORE — broken in Safari */
.grad-text {
  background: linear-gradient(90deg, var(--lime) 0%, #fff 40%, var(--lime) 80%);
  background-size: 200% auto;
  background-clip: text;
  color: transparent;
  animation: gradmove 3.5s linear infinite;
}

/* AFTER — works in Safari */
.grad-text {
  background: linear-gradient(90deg, var(--lime) 0%, #fff 40%, var(--lime) 80%);
  background-size: 200% auto;
  -webkit-background-clip: text; /* Safari */
          background-clip: text;
  -webkit-text-fill-color: transparent; /* Safari — NOT color: transparent */
  color: transparent; /* Fallback for non-Safari */
  animation: gradmove 3.5s linear infinite;
}
Fix 05
Sticky Word Builder P2 High
Priority
P2
First pass
What breaks
The pinned word-building statement doesn't stick in Safari. The user scrolls straight through the section without the content pinning in place. All 15 words appear simultaneously and instantly — the whole scroll-driven narrative is broken.
Why
Safari has documented bugs with position: sticky inside display: grid parents. The sticky child computes its containing block incorrectly. The fix is to change the parent from grid to block, and ensure no ancestor has overflow: hidden (which also breaks sticky in Safari).
/* BEFORE — breaks Safari sticky */
#word-build {
  position: relative;
  height: 500vh;
  display: grid; /* ← THIS breaks sticky in Safari */
}

/* AFTER — display: block fixes it */
#word-build {
  position: relative;
  height: 500vh;
  display: block; /* Safari sticky works correctly inside block */
}

#word-build-sticky {
  position: sticky;
  top: 0;
  height: 100svh;
  height: 100vh; /* fallback */
  overflow: hidden; /* Needed for Safari — define the stacking context */
  display: flex;
  align-items: center;
  justify-content: center;
}
Also check

Make sure no ancestor element of #word-build has overflow: hidden or overflow: auto set. In Safari, any overflow value other than visible on an ancestor will break position: sticky on a descendant — even if the overflow is set many levels up the tree.

Fix 06
Variable Font Weight on Scroll P2 High
Priority
P2
First pass
What breaks
The scroll-driven headline font-weight change does nothing in Safari. The H1 stays at weight 900 regardless of scroll position.
Why
Safari sometimes ignores font-variation-settings set via JS if the font isn't fully ready when the property is first applied. Safari also requires that the @font-face declaration includes font-weight: 100 900 (the full range) to recognise the font as variable — without this it treats it as a static font and ignores the variation axis.
/* Ensure @font-face declares the full weight range */
@font-face {
  font-family: 'Big Shoulders Display';
  src: url('/fonts/BigShouldersDisplay-VariableFont_wght.ttf') format('truetype');
  font-weight: 100 900; /* ← CRITICAL — tells Safari it's a variable font */
  font-style: normal;
  font-display: swap;
}

// Wrap the scroll listener in document.fonts.ready
// Safari needs fonts fully loaded before accepting fontVariationSettings via JS
export function initFontWeightScroll() {
  const headline = document.getElementById('hero-hl')
  if (!headline) return

  document.fonts.ready.then(() => {
    // Fonts confirmed loaded — now safe to set fontVariationSettings
    window.addEventListener('scroll', () => {
      try {
        const heroEl = document.getElementById('hero')
        const heroH = heroEl?.offsetHeight ?? innerHeight
        const progress = Math.min(Math.max(scrollY / heroH, 0), 1)
        const weight = Math.round(900 - progress * 800)
        headline.style.fontVariationSettings = `'wght' ${weight}`
        headline.style.letterSpacing = `${-0.01 + progress * 0.04}em`
      } catch (e) {
        // Safari can throw if font transitions aren't ready — silently skip
      }
    }, { passive: true })
  })
}
Fix 07
clip-path Animations P2 High
Priority
P2
First pass
What breaks
Work section wipe and swipe scroll reveals are either invisible, instantly visible (no animation), or jank heavily on Safari. The shuffle transition column sweep also breaks.
Why
Safari supports clip-path but doesn't hardware-accelerate clip-path transitions the same way Chrome does. Without a GPU compositing hint (translateZ(0)), Safari repaints the clip-path change in software every frame, causing severe jank on complex layouts. Also requires -webkit-clip-path prefix for Safari 14 and below.
/* Add -webkit-clip-path prefix + GPU compositing hint to all animated clip-path elements */
.wipe {
  -webkit-clip-path: inset(0 0 100% 0); /* Safari 14 and below */
          clip-path: inset(0 0 100% 0);
  -webkit-transform: translateZ(0); /* Force GPU layer — prevents Safari jank */
          transform: translateZ(0);
  -webkit-backface-visibility: hidden;
          backface-visibility: hidden;
  transition:
    -webkit-clip-path 1.05s cubic-bezier(.16,1,.3,1),
            clip-path 1.05s cubic-bezier(.16,1,.3,1);
}
.wipe.in {
  -webkit-clip-path: inset(0 0 0% 0);
          clip-path: inset(0 0 0% 0);
}

.swipe {
  -webkit-clip-path: inset(0 100% 0 0);
          clip-path: inset(0 100% 0 0);
  -webkit-transform: translateZ(0);
          transform: translateZ(0);
  transition:
    -webkit-clip-path 1.05s cubic-bezier(.16,1,.3,1),
            clip-path 1.05s cubic-bezier(.16,1,.3,1);
}
.swipe.in {
  -webkit-clip-path: inset(0 0% 0 0);
          clip-path: inset(0 0% 0 0);
}

/* Shuffle overlay columns */
.shuffle-col {
  -webkit-transform: translateY(-100%);
          transform: translateY(-100%);
  will-change: transform; /* Promote to own GPU layer pre-animation */
}
Fix 08
mix-blend-mode on Cursor P2 High
Priority
P2
First pass
What breaks
The cursor dot uses mix-blend-mode: difference to invert colour against content. In Safari, when the cursor dot overlaps a hardware-accelerated layer (the Three.js WebGL canvas), it causes the entire page to flash or flicker with each cursor movement. On some Safari versions, the blend mode on a position: fixed element renders completely wrong.
Fix approach
Detect Safari in JS and remove the blend mode. The cursor still works visually — it just doesn't invert against content. This is an acceptable trade-off. On Safari, keep the cursor as a solid lime dot and ring without blending.
// In Cursor component — remove mix-blend-mode on Safari
import { isSafari } from '@/lib/browser'

useEffect(() => {
  const dot = document.getElementById('cdot')
  if (dot && isSafari) {
    dot.style.mixBlendMode = 'normal'
    dot.style.background = 'var(--lime)'
    // Make it slightly transparent so it doesn't occlude content
    dot.style.opacity = '0.85'
  }
}, [])

/* CSS-only alternative — use @supports to detect blend mode support */
@supports not (mix-blend-mode: difference) {
  #cdot {
    mix-blend-mode: normal;
    opacity: 0.85;
  }
}
Fix 09
position:fixed Jump on iOS P2 High
Priority
P2
First pass
What breaks
On iOS Safari during momentum scroll (especially at the top and bottom of the page), position: fixed elements — the pill nav, Lisa button, grain canvas, cursor, spotlight, and page background — appear to jump or slide briefly before snapping back to their fixed position.
Why
A long-standing iOS Safari rendering bug. During momentum scroll compositing, iOS moves the fixed element with the scroll momentarily before the next paint corrects it. Promoting the element to its own GPU compositor layer (via transform: translateZ(0)) moves it out of the main scroll compositing layer and eliminates the jump.
/* Apply GPU promotion to all position:fixed elements */
#pill-nav,
#lisa-btn,
#lisa-panel,
#grain,
#trail-canvas,
#page-bg,
#spot,
#cdot,
#cring,
#clabel,
#scrollprog {
  -webkit-transform: translateZ(0);
          transform: translateZ(0);
  -webkit-backface-visibility: hidden;
          backface-visibility: hidden;
}
Trade-off

Applying transform: translateZ(0) to many elements creates many GPU compositor layers, which uses more VRAM. On low-end iOS devices (iPhone SE, older iPads), too many promoted layers can cause a different problem — GPU memory pressure. Apply selectively to the elements most visible during scroll — pill nav, grain canvas, and page-bg — rather than every single fixed element.

Fix 10
Grain Canvas Memory Crash P3 Medium
Priority
P3
Before launch
What breaks
On iOS Safari the browser tab crashes silently — the page reloads with "A problem occurred with this webpage so it was reloaded." The grain canvas is regenerating a full-screen createImageData at 60fps, which allocates roughly 8MB per frame on a 1920px-wide screen. iOS strictly limits canvas memory.
// Grain init — throttle heavily on iOS, disable entirely on very low-end devices
import { isIOSSafari, isMobile } from '@/lib/browser'

export function initGrain() {
  const canvas = document.getElementById('grain') as HTMLCanvasElement
  if (!canvas) return

  // On iOS Safari — use SVG filter instead of canvas (zero CPU, no crash risk)
  if (isIOSSafari) {
    canvas.style.display = 'none'
    const grainDiv = document.getElementById('grain-filter')
    if (grainDiv) grainDiv.style.display = 'block'
    return
  }

  const ctx = canvas.getContext('2d')!
  let W = innerWidth, H = innerHeight
  canvas.width = W; canvas.height = H

  // Throttle: 20fps on desktop, 12fps on mobile
  const interval = isMobile ? 5 : 3 // skip N frames between redraws
  let frame = 0

  function draw() {
    frame++
    if (frame % interval === 0) {
      const id = ctx.createImageData(W, H)
      const d = id.data
      for (let i = 0; i < d.length; i += 4) {
        const v = Math.random() * 255 | 0
        d[i] = d[i+1] = d[i+2] = v; d[i+3] = 255
      }
      ctx.putImageData(id, 0, 0)
    }
    requestAnimationFrame(draw)
  }
  requestAnimationFrame(draw)
}

Add the SVG grain filter to your layout — this is the iOS Safari fallback:

/* iOS Safari sees this, Chrome/Brave see the canvas */
#grain-filter {
  display: none; /* hidden by default — JS enables on iOS Safari */
  position: fixed;
  top: 0; right: 0; bottom: 0; left: 0;
  z-index: 9000;
  pointer-events: none;
  opacity: .04;
  mix-blend-mode: screen;
  filter: url(#noise);
}

<!-- Add to layout — hidden SVG filter definition -->
<svg style="display:none">
  <filter id="noise">
    <feTurbulence type="fractalNoise" baseFrequency="0.85"
      numOctaves="4" stitchTiles="stitch"/>
    <feColorMatrix type="saturate" values="0"/>
  </filter>
</svg>
<div id="grain-filter"></div>

Fix 14
Lenis on iOS Safari P3 Medium
Priority
P3
Before launch
What breaks
On iOS Safari, Lenis can cause a "double scroll" sensation at the top and bottom of the page — the iOS native rubber-band overscroll bounce fights with Lenis's momentum, making the scroll feel unstable or twitchy at the edges of the page.
// LenisProvider.tsx — update config for Safari compatibility
import { isIOSSafari, isSafari } from '@/lib/browser'

const lenis = new Lenis({
  lerp: isIOSSafari ? 0 : 0.075, // 0 = native scroll on iOS, no Lenis lerp
  duration: 1.2,
  easing: (t) => t === 1 ? 1 : 1 - Math.pow(2, -10 * t),
  smoothWheel: !isSafari, // disable smooth wheel on all Safari — native handles it better
  smoothTouch: false,     // NEVER override iOS touch scroll
  touchMultiplier: 0,
  syncTouch: false,
  overscroll: false,
})

/* Prevent rubber band fighting Lenis at page edges */
html {
  overscroll-behavior-y: none; /* Only on the root — prevents edge bounce conflict */
}
Trade-off

Setting lerp: 0 on iOS means Safari users get native scroll instead of the gummy Lenis feel. This is intentional — iOS Safari's native momentum scroll is already excellent, and fighting it creates a worse experience than native. Desktop Safari still gets Lenis with smoothWheel: false which gives a good feel without the rubber-band conflict.

Fix 15
flex gap on Safari 13 P3 Medium
Priority
P3
Before launch
What breaks
gap in flexbox (not grid) wasn't supported until Safari 14.1. Any display: flex container using gap for spacing between items will have no spacing on Safari 13. This primarily affects: service mini row, footer links, CTA buttons row, cover-meta strip.
How common
Safari 13 is very rare in 2025 — mostly users on macOS Mojave who can't update. Analytics will tell you if it's worth fixing. Use @supports to add margin fallbacks only when gap isn't supported.
/* @supports fallback for flex gap */
@supports not (gap: 1px) {
  /* Footer links */
  .foot-links a + a { margin-left: 24px; }

  /* CTA buttons */
  .cta-acts > * + * { margin-left: 14px; }

  /* Hero actions */
  .hero-acts > * + * { margin-left: 12px; }

  /* Service pills */
  .svc-pills > * + * { margin-left: 6px; }
}
